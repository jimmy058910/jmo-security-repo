# Release & CI/CD Pipeline Rules

**What this covers:** GitHub Actions workflows, release process, Docker multi-arch builds, version management, and release troubleshooting.

## GitHub Actions Example

```yaml
- run: jmo scan --repo . --results-dir results-baseline
- run: jmo scan --repo . --results-dir results-current
- run: jmo diff results-baseline/ results-current/ --format md > diff.md
```

## GitHub Actions Workflows (4-Workflow Structure)

Consolidated from 8 workflows:

| Workflow | File | Trigger | Purpose |
|----------|------|---------|---------|
| **CI** | `ci.yml` | PR / push to main | Lint, unit tests, adapter tests, coverage |
| **Scheduled** | `scheduled.yml` | Cron / manual | Nightly e2e, tool-update checks, security scans |
| **Release** | `release.yml` | Tag push (`v*`) | Build images, publish to registries, GitHub release |
| **Maintenance** | `maintenance.yml` | Manual / cron | Dependency updates, Docker image pruning |

**Scheduled job pattern:** All `scheduled.yml` jobs that run pytest MUST use the canonical install block — `astral-sh/setup-uv@v9.0.0` (with `version: "0.11.15"`, `python-version: '3.12'`, `cache-dependency-glob: "uv.lock"`), then `uv sync --locked --group dev`, then the venv-on-PATH step. Reference pattern: the `e2e-tool-integration` job. Omitting dev deps causes `--json-report` to fail silently. Anything pytest must *import* (plugins like `pytest-playwright`) has to enter `.venv` via `uv sync --extra <name>` — uv venvs ship no pip, so a bare `pip install` lands in the runner's system Python and the plugin is invisible to `.venv`'s pytest. Bare `pip install` of a standalone CLI tool (semgrep, checkov, yamllint...) invoked as its own binary is unaffected.

**Windows PATH trap:** the venv-on-PATH step MUST use `cygpath -w` for the `.venv/Scripts` branch. `$PWD` in Git Bash on Windows is a POSIX path. Git Bash resolves POSIX `PATH` entries itself, so `python -m pytest` still runs and thousands of tests pass — but the Python process inherits the raw `PATH` string, and `shutil.which()` on Windows cannot interpret `/d/a/...`, so every external-tool lookup silently returns `None`. Symptom: only tool-discovery tests fail (e.g. `test_scan_skips_missing_tools_and_runs_available` → `assert 1 == 0`) while everything else is green.

**`astral-sh/setup-uv` has no floating major tag past v7.** `v8` and `v9` exist only as full semver (`v9.0.0`). `@v9` fails every job in ~2s with `Unable to resolve action ..., unable to find version v9`.

## Release Process

**CRITICAL:** All tools MUST be updated before release (CI enforces this).

1. **Automated (recommended):** GitHub Actions → Release workflow (tag push triggers `release.yml`).
2. **Manual:** Update tools → bump version → tag → push.
3. **Hotfix to main:** Must go through a PR (GitHub rulesets enforce `quick-checks`). Cannot push directly.

**Version management commands:**

```bash
python3 scripts/dev/update_versions.py --check-latest  # Check updates
python3 scripts/dev/update_versions.py --sync          # Sync Dockerfiles
```

**NEVER manually edit tool versions in Dockerfiles.** See [docs/VERSION_MANAGEMENT.md](../../docs/VERSION_MANAGEMENT.md).

See [docs/RELEASE.md](../../docs/RELEASE.md) for the detailed release guide.

## Release Workflow Architecture (v1.0.0+)

The release pipeline has 3 phases triggered by a `v*` tag push:

```text
Pre-Release Validation → PyPI Publish → Docker Build (8 parallel: 4 variants × 2 arches)
                                      → Homebrew (existence check, skip if not in homebrew-core)
                                      → WinGet (existence check via GitHub API, skip if not in winget-pkgs)
                                      → Badge Verify
                         Docker Build → Docker Merge (4 parallel: create multi-arch manifests)
                         Docker Merge → Docker Scan + Benchmarks + Docker Hub README
```

### Multi-Arch Docker Builds (CRITICAL Details)

**Native runners (no QEMU):**

- `docker-build-amd64`: `runs-on: ubuntu-latest` (native x86_64).
- `docker-build-arm64`: `runs-on: ubuntu-24.04-arm` (native ARM).
- `docker-merge`: downloads both digests, creates GHCR manifest via `imagetools create`, replicates to Docker Hub/ECR via `crane copy`.

**GHCR is the primary registry.** `imagetools create` targets GHCR only (cross-registry blob copy doesn't work). Docker Hub and ECR are replicated via `crane copy --platform all` with `continue-on-error: true`.

## Release Troubleshooting

| Issue | Solution |
|-------|----------|
| Tag push fails | Main has rulesets — must PR through CI, then tag |
| Docker build cache stale | `gh cache delete --all --repo owner/repo` then re-tag |
| scancode fails on arm64 | Expected — `extractcode-7z` has no arm64 wheel. Conditional install via `TARGETARCH` check |
| Homebrew/WinGet fail on first release | Both have existence checks that skip gracefully. Submit initial manifests manually. |
| `verify_badges.sh` fails on new branch types | Add branch prefix to allowlist at `scripts/dev/verify_badges.sh:100` (currently: dev, feature, refactor, hotfix, dependabot) |
| `jmo validate` fails on Linux but passes locally | Platform-specific checks (e.g., `path-mixed-separators`) — guard with `sys.platform` |
| Tool version 404 in Docker build | Run `python scripts/dev/update_versions.py --validate` to check all URLs, then `--sync` |
| Scheduled e2e jobs fail with "no test results" | Likely missing the `uv sync --locked --group dev` install block (or its venv-on-PATH step) — compare against `e2e-tool-integration` job pattern |
| `E2E Visual Dashboard Tests` dies in seconds: `collected 0 items / 1 skipped`, then `make: *** Error 5` | pytest exit 5 = nothing collected. `test_dashboard_visual.py` opens with `pytest.importorskip("playwright")`, and playwright isn't importable from `.venv`: uv-created venvs ship **no pip**, so the job's old bare `pip install pytest-playwright` resolved to the runner's *system* pip while `make test-e2e-visual` runs `.venv`'s python (Makefile prefers `.venv` when present). Broken by the uv.lock migration (#683 landed 07-29; identical cron failures 07-29 and 07-30). Fix: install pytest plugins through the lock — `uv sync --locked --group dev --extra visual`, then `uv run --no-sync playwright install chromium --with-deps`. `--no-sync` keeps the browser-install step from touching the env at all. (Measured nuance, uv 0.11.19: a plain `uv run`'s implicit sync is *inexact* by default and does **not** strip the extra — the flag is insurance against that default changing, and skips a pointless re-resolve.) Post-#683 rule of thumb: audit any bare `pip install` of an **importable** package in workflows; standalone CLI tools invoked as binaries are fine. |
| `Dependabot PR fails deps-compile freshness` (historical — cannot recur) | **Removed by the uv.lock migration (PR #683).** Until 2026-07-29 `requirements-dev.txt` was generated by `uv pip compile --universal` but *edited in place* by Dependabot's Linux-only pip resolver. The two serializers disagreed, so after every Dependabot merge `main` held a non-canonical lockfile and the next human PR failed a byte-equality gate with an unrelated-looking red (PRs #677 and #682 on the same day; #680 re-armed it). Worse, the pip resolve dropped `pywin32 ; sys_platform == 'win32'` (via `mcp`), silently breaking Windows dev installs. Successive attempts to scope the gate (PR #321 authorship check, PR #323 branch-ref check, then a single event-scoped predicate) all treated the symptom. The fix was removing the second writer: dev deps now live only in `pyproject.toml`'s `[dependency-groups]`, `uv.lock` is the only lockfile, and Dependabot runs on the `uv` ecosystem so it regenerates the lock *with uv*. The gate is now `uv lock --check`, runs **unconditionally** on every event and author, and bot and human PRs are resolver-symmetric. If it fails: `make deps-lock && git add uv.lock`. |
| A from-scratch `uv lock` silently upgrades everything | Declarations are floors (`>=`), so regenerating the lock from nothing is an *upgrade*, not a translation. The migration's first resolve moved **30 of 94 packages**, including `mcp 1.28.1 → 2.0.0` (which swaps `httpx` for `httpx2` and drops `pydantic-settings`/`httpx-sse`) — changing ~100 tests' collection status and breaking `tests/integration/test_cli_scan_ci.py`. Add an upper bound only to hold back a known-breaking major (see `mcp[cli]>=1.0.0,<2`), and diff the package **set** before assuming equivalence: `uv export --frozen --quiet --format requirements.txt --no-emit-project --no-hashes -o new.txt`, then compare names first and versions second. |
| A `continue-on-error: true` job shows a green tick over real failures | `windows-2022` in `ci.yml:test-sharded` is non-blocking, so `gh pr checks` reports **pass** while the log says `1 failed`. When verifying a change that could plausibly affect Windows, read the job log (`gh run view --job <id> --log`) and compare `N passed / N skipped` against a `main` baseline — a shifted skip count is as much a signal as a failure. |
| Tool contract test fails after version bump | Automated version bumps can change output schemas. Run the tool against fixtures to verify, then update `result_item_keys` in `test_tool_contracts.py` |
| Windows matrix job fails with `ParserError: Missing expression after unary operator '--'` | Multi-line `run:` block uses bash `\` line continuation; PowerShell (default on `windows-latest`) rejects it at parse time. Add `shell: bash` to the step. |
| Non-root container can't write to mounted dir in CI (`PermissionError`) | GitHub runner UID (1001) ≠ container `USER jmo` UID (1000); bind mounts preserve host UID. Fix: `chmod 777` the host dir before mount, or add `--user $(id -u):$(id -g)` to `docker run`. |

| Pre-existing actionlint findings accumulate unseen on PRs, only surface in scheduled full-lint | `reviewdog/action-actionlint` in ci.yml:29 defaults to `filter_mode: added` — only reports findings on lines changed in the PR diff. Pre-existing info/error findings in workflow files that the PR didn't touch are silently skipped. The scheduled.yml "Lint (full pre-commit suite)" job runs `pre-commit run actionlint` against all files, so it catches the accumulated backlog — meaning once this job fails, you have to fix the *entire* backlog, not just newly-introduced findings. Mitigation option: `filter_mode: nofilter` on the reviewdog action (keeps `fail_level: error` so info findings are annotations not failures, but error-level findings fail CI even on unchanged lines). |
| Scheduled Lint yamllint fails on `./~/.cache/pre-commit/repo*/...` paths | A step-level `env:` block contains `PRE_COMMIT_HOME: ~/.cache/pre-commit`. GitHub Actions' `env:` does NOT shell-expand `~`, so pre-commit receives the literal string and creates a directory at `$PWD/~/.cache/pre-commit/`. A subsequent `yamllint -c .yamllint.yaml .` then descends into it and fails on third-party hook test fixtures. This also silently breaks the `actions/cache` step (its Node action DOES expand `~` to `/home/runner/.cache/pre-commit`, so the paths never match — cache has been useless). Fix: remove the `PRE_COMMIT_HOME` env line entirely; pre-commit's default (`$HOME/.cache/pre-commit` on Linux) matches the cache action's expanded path. |
| Nightly `test_docker_variant_scan` crashes with `PermissionError: [Errno 13] Permission denied: 'jmo.yml'` inside container | Python 3.12 changed `pathlib.Path.exists()` to propagate `PermissionError` (and other `OSError` subclasses besides `FileNotFoundError` / `NotADirectoryError`). Mark test chmod with `# nosemgrep: python.lang.security.audit.insecure-file-permissions.insecure-file-permissions` — 0o777 is intentional and tmp_path is run-scoped. |
| Nightly `test_docker_variant_tools[deep]` fails with rc=1 despite correct JSON output | `tools check --profile deep --json` (`scripts/cli/tool_commands.py:170-171`) returns 1 when any tool reports `installed: false`. The `deep` profile includes 4 tools in `MANUAL_INSTALL_TOOLS` (akto, afl++, mobsf, falco) that are intentionally NOT baked into the Docker image — so rc=1 is the correct behavior for a correctly-built deep container. Tests that hard-fail on `rc != 0` are wrong for this variant. Only hard-fail if JSON parsing fails (catastrophic). Balanced/slim/fast profiles have no manual-install tools so they return rc=0 as before — this is why only `deep` was affected. |
| `dependency-check` reports `installed: false` in `:deep`/`:balanced` images | `tool_registry.py:116` maps `dependency-check` → binary `dependency-check.sh` (the upstream canonical name from the zip distribution). Dockerfiles symlink only the bare `dependency-check` name at `/usr/local/bin/dependency-check`. When `tool_manager._find_binary("dependency-check.sh")` falls through to `find_tool()` (after the ~/.jmo/bin special-case branch misses), PATH search for literal `dependency-check.sh` doesn't match the bare symlink. Fix: add a second symlink `ln -s /opt/dependency-check-cli/bin/dependency-check.sh /usr/local/bin/dependency-check.sh` in both `Dockerfile.deep` and `Dockerfile.balanced`. | Docker image fixes (code in `scripts/`) don't propagate to nightly tests until next release | GHCR images `ghcr.io/jimmy058910/jmo-security:<variant>` are rebuilt ONLY on release tag push (`release.yml` triggers on `v*` tags). The scheduled nightly test pulls these pre-built images and runs `docker run <image> tools ...` — code changes merged to main via the CI workflow don't reach the container until the next release. Workaround: trigger manual rebuild via `release.yml` workflow_dispatch or tag a minor release. This means any `scripts/cli/` or `scripts/core/` fix for a Dockerfile-hosted bug requires waiting for or triggering a release to validate end-to-end. Test-level fixes (in `tests/e2e/`) ARE effective immediately because pytest runs on the host, not inside the container. |
| Bug archeology via `--maxfail` truncation | Nightly Extended Tests historically ran `pytest tests/ ... --maxfail=5` — once you fixed 1–5 visible failures, the next pass surfaced 5 *new* failures from deeper in the alphabetical test ordering, latent for releases but always invisible because earlier failures cut them off. Post-v1.0.3 stabilization ran through 5 such layers at the old threshold (PRs #343 → #344 → #345 → #346 → #347), each fixing 3-5 visible failures and revealing 0-4 new ones. **v1.0.5 raised the cap to `--maxfail=20` on `nightly-extended-tests` and the cross-platform jobs** (smoke kept at 5, requires_tools at 3 — small suites where early-stop is real signal), and added a `Summarize pytest failures` step that renders all caught failures (capped at 50) into the run's `$GITHUB_STEP_SUMMARY` plus archives `pytest-report.json` as an artifact. Truncation still possible at the new cap; when it happens, the Summary tab + artifact give you the full list at once instead of forcing a 5-PR archeology cycle. Iterate with `gh workflow run scheduled.yml --ref main -f task=nightly` (~12-15 min vs 24h cron). |
| `:latest` published tag = deep variant only; no `:latest-deep`, `:latest-slim`, etc. | Per `release.yml` metadata-action config, the `latest` tag uses `suffix=` (empty) override on the deep matrix job only. So GHCR has `:latest`, `:deep`, `:balanced`, `:slim`, `:fast`, `:1.0.3`, `:1.0.3-deep`, `:1.0.3-balanced`, etc. — but **no `:latest-VARIANT` tags**. Tests pinning to `:latest-full` or `:latest-deep` will fail with "manifest unknown" or pull a different variant than expected. Verify actual tags with `gh api users/OWNER/packages/container/IMAGE/versions --jq '.[0:3] \| .[] \| .metadata.container.tags'`. |
| `jmo ci --profile balanced` fails with `unrecognized arguments: balanced` | `--profile` is a boolean flag on the `ci` subcommand (`scripts/cli/jmo.py:337-339`, `action="store_true"` — controls timing collection). The flag for selecting a profile is `--profile-name` (line 196-200, value-taking), the same as `cmd_scan`. Tests/scripts that pass `jmo ci --profile <name>` parse `--profile` as boolean and `<name>` as an unrecognized positional. Fix: use `--profile-name` for profile selection. The CLI surface has overlapping prefixes — worth flagging as a CLI-design cleanup target. |
| `jmo history list` returns rc=1 on empty database | When the SQLite history DB has zero scans, `jmo history list` exits 1 (treats "nothing to show" as a non-success). Tests that assert `rc == 0` will fail when the test setup doesn't actually populate findings (e.g., `--allow-missing-tools` scans on a fast variant with no real scanners installed). The release.yml "Benchmark Docker Image Sizes" job emits compressed numbers — don't conflate the two. |
| `expected_tools` constants drift after a `PROFILE_TOOLS` change | When tools are removed from `PROFILE_TOOLS` (in `scripts/core/tool_registry.py`), several test/workflow constants need to follow: `tests/e2e/test_docker_workflows.py::DOCKER_VARIANTS`, `.github/workflows/scheduled.yml`'s validate-variants matrix, and named-tool lists like `DEEP_EXPECTED_TOOLS`/`DEEP_ONLY_TOOLS`. When changing `PROFILE_TOOLS`, grep for `expected_tools` and the variant counts (`14`, `18`, etc.) in tests + workflows simultaneously. |
| `MANUAL_INSTALL_TOOLS` binaries appear in DEEP_ONLY_TOOLS / DEEP_EXPECTED_TOOLS test lists | `afl++` (binary `afl-fuzz`), `mobsf`, `akto`, `falco` are in `PROFILE_TOOLS["deep"]` BUT in `MANUAL_INSTALL_TOOLS` — listed in the registry but intentionally NOT baked into Docker images. | Nightly Extended Tests workflow needs `-m "not requires_tools and not smoke"` filter | Without this filter, `pytest tests/` runs ALL tests including ones decorated `@pytest.mark.requires_tools` (need real scanners installed — exercised by the `e2e-tool-integration` job that installs them) and `@pytest.mark.smoke` (need `pip install jmo-security` released package — exercised by separate smoke-test workflow). | `Install security tools` step fails with `aquasecurity/trivy crit unable to find ''` (or similar for grype/syft/trufflehog) | Upstream `install.sh` scripts (`raw.githubusercontent.com/.../main/.../install.sh`) call GitHub's API at runtime to discover the "latest" release tag. When the API transiently fails (CDN flake, rate limit), the script emits "unable to find ''" and exits 1 — breaking CI for changes that have nothing to do with the affected workflow. Hit `commit 62bc02b` on 2026-04-26 (run `24959553419`). The `releases/latest/download/...` redirect pattern has the same drift class — version isn't pinned so what gets installed differs across runs. **CI install hardening convention** (extends `.claude/rules/docker.rules.md` "Download Hardening Convention"): pin every install to a specific version from `versions.yaml`, declared via job-level `env:` block (e.g., `TRIVY_VERSION: "0.70.0"`), and download the explicit release URL with `curl -fsSL --retry 3 --retry-delay 5 --retry-all-errors --connect-timeout 30 --max-time 600` + `gzip -t` integrity check before extraction. NEVER use `\| sh` script-pipes from upstream installers in CI. The `versions.yaml` value is the source-of-truth — update both files together when bumping. **yamllint trap**: long URL lines with `${TRUFFLEHOG_VERSION}` substituted twice exceed the 140-char line-length limit; alias to short var `v="$TRUFFLEHOG_VERSION"` immediately before the `curl` and use `${v}` in the URL. yamllint disable-line directives don't work inside `run: \|` block scalars (they're treated as bash comments). |
| `coverage-aggregate` reports a coverage value lower than `make test` and drifts when test files change without `scripts/` changes | Two compounding bugs in `ci.yml`'s `coverage-aggregate` step: (1) `process_package` used `classes = pkg.find('classes') or pkg.findall('class')` followed by `if hasattr(classes, '__iter__'):` — but `xml.etree.ElementTree.Element` uses the legacy `__getitem__` iteration protocol and does NOT define `__iter__`, so `hasattr(..., '__iter__')` is False and the merge loop is silently skipped for every package in cobertura-nested XMLs. Result: `merged_files` stays empty, base_root is unmodified, `coverage.xml` is byte-identical to shard-1. (2) Even if bug #1 didn't exist, the root `<coverage>` element's `line-rate`/`lines-valid`/`lines-covered` attributes are never recomputed after the merge — the threshold check reads `root.get('line-rate')` which remains at shard-1's standalone value (~68-72% since each shard runs ~1/4 of the suite) instead of the true merged aggregate (~88%). Symptom: coverage "drops" by 1-3 points whenever `pytest-split --splitting-algorithm least_duration` reshuffles tests (i.e. any time a new test file is added), with no `scripts/` changes. Verify by downloading shard XMLs and computing `covered/total` from `<line>` elements per-shard vs. for the merged set — pre-fix, the merged set equals shard-1; post-fix, it's the OR-union (~88%). When investigating future "drops," ALWAYS download artifacts and compute the true merged value before adjusting thresholds. The bug existed since the sharded-coverage approach was introduced; PRs #350-#354 only made it more visible because they added enough test files to reshuffle shards noticeably. Codecov's parser reads `<line>` elements directly and reported accurate aggregate numbers throughout — only the local threshold check was broken. |
| `gh pr checks` shows a failure you cannot reproduce, or a fix that satisfies CI one push and fails the next | **Every branch push produces TWO `ci.yml` runs** — one `event=push`, one `event=pull_request` — and `gh pr checks` aggregates both. They see different worlds: `pull_request` gets a **shallow checkout of the merge commit** (so `git log -1` is `Merge <sha> into <sha>`, and parents are NOT fetched, making `HEAD^2` unavailable), while `push` gets the real tip and has **no** `GITHUB_HEAD_REF` and no PR payload. On both, `git rev-parse --abbrev-ref HEAD` returns `HEAD` (detached). Always run `gh run list --json databaseId,event,headSha` and identify *which event* the failing job belongs to before diagnosing. Fixing one event type at a time and re-pushing burned 3 CI cycles on PR #713. |
| `quick-checks` fails at `Verify PyPI badge version matches pyproject.toml` on a release PR | `verify_badges.sh`'s `^release: v` exemption reads `git log -1`, which on a PR is the **merge** commit — so the exemption **had never once fired on a PR** in the repo's history (measured on #713: no exemption line printed at all). Fixed in v1.0.8 by keying off the **PR title** from `$GITHUB_EVENT_PATH` (checkout- and ordering-independent, and the same string the squash-merge subject becomes) while keeping the `git log -1` path for `push`/tag runs. **Consequence to respect: the release commit must remain the branch tip** — a review fixup committed on top of it silently re-arms the check on the `push` run. |
| `main` goes red on the badge check right after merging a release PR | Expected, and it resolves when the tag publishes to PyPI — the check literally prints `Action needed: Tag and release vX.Y.Z`. **But** merging any further commit onto `main` before tagging (e.g. a Dependabot PR) makes the new tip a non-release subject, so the exemption cannot fire there either. Verify the **only** failing step is the badge one, then tag. Note a still-open gap: on a `push` run `current_branch` resolves to `HEAD`, so the `dependabot/`/`chore/`/`feature/` branch allowlist never matches — harmless while local == PyPI, red whenever `main`'s version is ahead. |
| `uv lock --check` fails on a release PR that changed no dependencies | `uv.lock` pins the **project's own** version (`name = "jmo-security"` / `version = "X.Y.Z"`), so a version bump alone makes the lock stale — verified on the 1.0.8 bump, where the check failed on nothing but the three version edits. Always `make deps-lock` and commit `uv.lock` in the same PR as the bump. A local `uv sync` refreshes it silently, so the drift stays invisible until CI. |
| A Dependabot PR opens against the **wrong base**, and retargeting it does not stick | **Dependabot reads `.github/dependabot.yml` from the repository's DEFAULT branch**, not from the branch it would target. So a `target-branch:` added on `dev` is inert until `dev` reaches `main` — it only starts working *after* the release it was written to protect (measured 2026-08-18: `git show origin/main:.github/dependabot.yml \| grep -c target-branch` → **0**, while `dev` set it on all five ecosystems in #829). Three consequences, each measured on PRs #882-#886. **(1) `gh pr edit --base dev` does not re-run CI** — every check-run kept its original `started_at`, because `ci.yml` triggers on `push`/`pull_request` with default activity types and a base change fires neither, so the green tick you are reading was computed against the *old* base. Confirm with `gh api repos/O/R/commits/<sha>/check-runs --jq '.check_runs[].started_at'`; force a real run with `gh pr close` + `gh pr reopen`, which fires `reopened`. **(2) Dependabot keeps evaluating against its configured target** regardless of the PR's actual base — it replied *"The base commit for this pull request has not changed."* to a rebase on three retargeted PRs. **(3) `@dependabot rebase` on a retargeted PR can self-close it** — it closed #886, deleted its branch, and reopened the same bumps as #893 against `main`; `gh pr reopen` then fails, though the head survives as `refs/pull/<N>/head`. **Do not send it.** Port the content as your own commits instead of fighting the targeting. Sibling of the self-close-after-conflicting-merge behaviour. |
| A Dependabot **github-actions** bump reddens Dockerfile lint on files it does not touch | A linter action bump can carry a new linter *ruleset*. `hadolint/hadolint-action` v3.3.0 → v3.4.0 ships hadolint v2.15.0, which flags pre-existing content (`DL3066` non-numeric user-id, `DL3025` CMD/ENTRYPOINT JSON notation). `quick-checks` fails at the **first** Dockerfile, so the remaining variants are never linted — expect more findings after fixing the first. Treat these as a Dockerfile remediation PR, not a dependency bump, and audit all four variants together; `DL3066`'s numeric-UID fix interacts with the UID-1000-vs-runner-1001 bind-mount behaviour and images only rebuild on a release tag. Same class as the unpinned-ruleset ambush fixed in #678. |
| An integration test that shells out to `jmo scan` times out, and raising the timeout does not help | Check the test's budget against the **scan's own** per-tool bound before touching it. `get_tool_timeout()` returns `max(default, tool_minimum)`; the `deep` default is 600s with floors to 1200s (`dependency-check`, `scancode`), so a 280s test ceiling was 2–4× *smaller* than the scan's — the test could never observe bounded behaviour. `--timeout` cannot lower a floor (measured: `dependency-check` still running at **5m30s** under `--timeout 30`); only a `per_tool` entry in the config can (same tool, **19s** under a 15s cap). **Do not over-tighten**: a 30s cap killed `semgrep` (natural runtime 47s) mid-write after it had already produced its output file, so the reconciler correctly reported it `contradictory` (`output` + `failed`). A cap that kills a healthy tool fabricates a defect instead of testing for one. |
| A test that shells out times out or errors locally but passes in CI | The **launch shell is part of the environment**. A suite launched detached from PowerShell inherits a PATH without Unix utilities; `tests/unit/test_tool_runner.py` uses `sleep` as its fake tool, which is not a native Windows binary, and produced 20 failures that became **59 passed, 3 skipped** when re-run under Git Bash (`/usr/bin/sleep`). Before calling a local failure a regression, re-run it in isolation *and* say which shell produced the number. |
| The badge check still reports the OLD PyPI version minutes after a successful publish | **PyPI's JSON API is CDN-edge cached**, so `https://pypi.org/pypi/<pkg>/json` can serve a stale version to one runner while another already sees the new one. Measured immediately after the v1.0.8 publish: a local query returned `1.0.8`, shields.io (which itself reads PyPI) rendered `1.0.8`, and a runner four minutes later still read `1.0.7` — same package, same moment. **Tell it apart from a genuinely unpublished release by the `Badge version (shields.io)` line the script already prints**: if the badge says the new version and `PyPI version` says the old one, it is cache lag, not a failed upload. Re-run the job rather than investigating; confirm with `pip index versions <pkg>` or the release workflow's own publish step, which is authoritative. |

## Re-Tag Cycle (When Release Workflow Fails)

```bash
git tag -d v1.0.0 && git push origin :refs/tags/v1.0.0  # Delete tag
# ... merge hotfix PR to main ...
git checkout main && git pull origin main                 # Sync main
git tag -a v1.0.0 -m "..." && git push origin v1.0.0     # Re-tag + push
git checkout dev && git merge origin/main && git push origin dev  # Sync dev
```
