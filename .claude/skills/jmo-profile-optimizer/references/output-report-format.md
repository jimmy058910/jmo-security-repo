# Output Report Format Reference

Template and example for the `OPTIMIZATION_REPORT.md` generated by the final
phase.

> Parse figures come from the **report phase** (`jmo report --profile`); tool
> run times and timeouts come from the **scan phase** (`scan-timings.json`).
> Whole-scan durations come from `jmo history`. See
> [optimization-patterns.md](optimization-patterns.md#phase-1-load-and-analyze-timingsjson).

---

## Report Template

```markdown
# Timing Optimization Report

**Baseline label:** juice-shop
**Report run:** 2026-08-05 14:30:00
**Aggregation wall clock:** 3.402s
**Cumulative parse time:** 12.100s across 5 tools (max_workers: 8)

---

## Baseline Comparison

| Metric | Current | Baseline (2026-07-02) | Change |
|--------|---------|-----------------------|--------|
| Cumulative parse time | 12.100s | 8.900s | +36.0% |
| trivy mean parse | 0.315s | 0.244s | +29.1% |
| semgrep mean parse | 0.324s | 0.401s | -19.2% |
| grype mean parse | 0.088s | n/a | no sample |

**Status:** PARSE-TIME REGRESSION — trivy findings rose from 2,950 to 4,310, so
the extra parse time tracks finding volume rather than adapter slowdown.

---

## Scan Phase (scan-timings.json)

| Tool | Runs | Timed out | Longest run | Worst share of wall clock |
|------|------|-----------|-------------|---------------------------|
| semgrep | 1 | 1 | 900s | 94.0% (juice-shop) |
| trivy | 1 | 0 | 212s | 22.1% (juice-shop) |

Shares are of that target's `wall_seconds`, not of the summed durations — tools
run concurrently, so the sum overstates the scan.

---

## Bottlenecks

Shares are of **cumulative parse time** (12.100s), not of wall clock — jobs run
in parallel, so shares of wall clock would not sum to 100%.

| Tool | Parse time | % of cumulative | Parses | Findings | Mean | p50 | p95 |
|------|-----------|-----------------|--------|----------|------|-----|-----|
| trivy | 7.240s | 59.8% | 23 | 4310 | 0.315s | 0.288s | 0.981s |
| semgrep | 3.890s | 32.1% | 12 | 1204 | 0.324s | 0.301s | n/a |
| grype | 0.612s | 5.1% | 7 | 88 | 0.087s | 0.084s | n/a |

`n/a` means the sample was too small for that percentile (20 parses for p95,
100 for p99). It is never a substitute for a value derived from the maximum.

---

## Recommendations

### Immediate (P1)

**1. Give semgrep a budget it can finish inside**

    per_tool:
      semgrep:
        timeout: 1200

**Evidence:** semgrep's row is `failed` with reason `timed out` on juice-shop after 900s (its floor in
`TOOL_TIMEOUT_DEFAULTS`), so that target lost every semgrep finding.

**2. Align the report worker count**

    jmo report ./results --threads 8

**Evidence:** the run used `max_workers: 4`, while `recommended_threads` is 8
(derived from CPU count, clamped by `profiling_min_threads` /
`profiling_max_threads` in `scripts/core/config.py`).

### Short-Term (P2)

**3. Profile the trivy adapter's parse path**

**Evidence:** 7.240s over 23 files (59.8% of cumulative parse time), 4,310
findings.

### Long-Term (P3)

**4. Reduce trivy finding volume at source**

**Evidence:** 4,310 findings dominate both parse time and downstream
deduplication. Tune the tool's own severity and ignore behaviour before
optimizing the adapter.

---

## Updated Configuration

    # jmo.yml -- top-level timing keys and per-tool overrides only.
    # The tool list lives in scripts/core/tool_registry.py:TOOL_MATRIX
    # (single source of the default). Omitting `tools:` keeps it.

    threads: 8
    timeout: 600
    per_tool:
      semgrep:
        timeout: 1200
      trivy:
        timeout: 900
        flags: ["--skip-dirs", "vendor,node_modules", "--cache-dir", "~/.cache/trivy"]

---

## Next Steps

1. Apply the configuration changes
2. Re-run `jmo scan` then `jmo report --profile`
3. Compare against the stored baseline
4. Store the updated baseline (automatic, final phase)

**Verifying a timeout change:** `timings.json` cannot confirm it — it records
report-phase parsing only. Read that tool's `seconds`, `state` and `reason` in
`scan-timings.json` before and after. Do not judge it by whole-scan duration
alone: a cap tight enough to kill a healthy tool makes the scan *faster* while
producing `failed` with reason `timed out`, and no findings.

---

**Memory:** baseline loaded from 2026-07-02; updated baseline stored after this run.

**Generated by:** jmo-profile-optimizer
```

## Report Sections Explained

| Section | Purpose |
|---------|---------|
| Header | Baseline label, run date, aggregation wall clock, cumulative parse time |
| Baseline Comparison | Current vs stored baseline, with `no sample` where no denominator exists |
| Scan Phase | Per-tool runs, timeouts, longest run and worst share of a target's wall clock, from `scan-timings.json` |
| Bottlenecks | Tools above 30% of cumulative parse time, with real percentiles |
| Recommendations | Prioritized actions, each citing the measurement behind it |
| Updated Configuration | Ready-to-paste `jmo.yml` per-tool overrides |
| Next Steps | Applying and verifying the changes |

**Rates are optional.** A per-tool timeout or failure rate needs many scans. It
comes from the history database's `scan_tool_runs` table (`jmo history query`),
which holds scans stored since v2.0.0. Include it when the history has enough
scans, and say how many. Per-tool outcomes **for a single scan** are always
available — see
[optimization-patterns.md Phase 4](optimization-patterns.md#phase-4-timeout-and-failure-analysis).
