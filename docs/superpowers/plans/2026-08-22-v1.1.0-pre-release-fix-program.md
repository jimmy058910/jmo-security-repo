# v1.1.0 pre-release fix program

> **For agentic workers:** this is a **program** plan, not a task plan. It fixes
> the order and the boundaries; each phase gets its **own** measured plan written
> at the time it is executed, after the measuring described in that phase's
> "Measure first" block. Do **not** expand a phase into TDD tasks from this
> document alone — see [Why there are no task-level steps here](#why-there-are-no-task-level-steps-here).

**Goal:** fix every open defect in `jmo-security` before tagging v1.1.0, in an
order where each phase's verification can be trusted and no phase invalidates an
earlier one.

**Architecture:** phases are ordered by three constraints, in priority order —
**instruments before measurements**, **delete before refactor**, and
**upstream before downstream** along the data pipeline
(`adapters → fingerprint dedup → enrich → compliance → EPSS → suppression → reporters`).
The pipeline constraint is the audit campaign's own hard-won ordering lesson,
applied to fixes instead of audits.

**Tech Stack:** Python 3.12, pytest (+xdist, +split), uv/`uv.lock`, GitHub
Actions, Docker (WSL only on this machine), `gh` CLI.

**Spec:** [2026-08-08-v1.1.0-audit-campaign.md](2026-08-08-v1.1.0-audit-campaign.md)
(release bar and cadence) and
[its tracker](2026-08-08-v1.1.0-audit-campaign-tracker.md) (per-issue evidence,
chunks 0-22). This program supersedes the campaign's *disposition* bar with a
**fix** bar, for the reason in [Why this replaces the disposition bar](#why-this-replaces-the-disposition-bar).

## Global Constraints

Copied verbatim; every phase's requirements implicitly include these.

- **Backward compatibility is NOT a constraint.** There are essentially no users.
  Do not weight "this would break existing users, baselines, pinned tags, or
  `history.db` rows" in any decision. The constraints are **time and evidence**.
- **Pre-commit order:** Black runs before Ruff. `make fmt && make lint && make test`
  before every commit. (`make` is **not on PATH** on this machine — invoke the
  underlying commands or `pre-commit run`.)
- **No `shell=True`** in subprocess calls, ever.
- **Conventional commits**, no trailers, no AI-attribution markers.
- **Never commit directly to `dev`.** Branch, PR into `dev`, squash.
- **Closing keywords go in an individual COMMIT message.** On a PR into `dev`
  the PR body is inert — not "linked but not yet closing", *inert*. Measured and
  corrected 2026-08-26; full evidence in
  [Closing keywords: what actually fires](#closing-keywords-what-actually-fires).
  A bare `#N` is still only a cross-link. Build any list mechanically and diff it
  case-insensitively — a `grep -oE 'closes #'` misses a capitalised
  `Closes #538`.
- **CI's only enforced coverage floor is 85%** (`coverage-aggregate`'s "Verify
  coverage threshold" step) — raised from 80 in Phase 1 (#756) after measuring
  86.87% on the marker-filtered suite. Cite the job and step, never a
  line number: that citation read `ci.yml:734`, `:788` and `:816`, and was stale
  at two of the three. Nothing sets `--cov-fail-under`, so there is still no
  local gate.
- **Run local suites with `PYTHONUTF8` unset.** CI pins it to `1`, an environment
  no real Windows user has; setting it hides the entire console-encoding class.
- **Bound local runs:** `JMO_THREADS=2 .venv/Scripts/python.exe -m pytest tests/ -n 8 -q
  -m "not smoke and not requires_tools and not docker"`. Unbounded `-n auto`
  manufactures failures (#767).
- **Read the `windows-2022` job log, never its check tick** — it is
  `continue-on-error: true` and reports green over exit code 1. Diff the **skip**
  count as well as passes.
- **Check both CI events.** Every push runs `ci.yml` twice (`push` and
  `pull_request`) and they see different worlds. A flake fails one; a regression
  fails both.
- **Mutation-test every guard.** A guard that survives its own defect must be
  fixed or deleted. Give each a negative control, and restore from a **file
  backup**, never `git checkout --`.

## Why this replaces the disposition bar

The campaign's release bar was deliberately a **disposition** bar: *"requiring 40
fixes before a release is how a campaign stops shipping."* That reasoning assumed
fixes were expensive and shipping was urgent.

Neither holds. There are essentially no users, and v1.1.0 is effectively the
first release — so there is nobody waiting, and "breaks existing behaviour" is
not a cost. Deferring 93 issues to protect a release nobody is waiting for
optimises for the wrong thing. **The disposition labels are not wasted**: they
are the queryable input to this program, and they remain the historical record of
what chunk 22 decided and why.

## Why there are no task-level steps here

`CLAUDE.md`: *"A plan written without running anything is a set of predictions,
not a spec. The #694 encoding plan had 8 measured-false claims, including a
reproduction that could never fail and a scoping premise that turned out nearly
disjoint from the actual failures (fixing all 153 fixed 0)."*

Expanding 80 issues into TDD tasks with concrete code, now, would manufacture
several hundred unmeasured predictions across subsystems this session has not
read. Each phase below therefore carries a **Measure first** block naming what to
establish before its detailed plan is written. That is the same shape the audit
campaign used — a strategy doc plus a tracker, with per-chunk detail added when
the chunk was reached — and it worked for 23 chunks.

## Ordering constraints (the load-bearing ones)

These are not preferences. Violating them wastes work:

1. **Phase 0 precedes everything.** You are about to make ~80 changes and verify
   them with a suite that currently drops 21 tests silently (#968), a `make lint`
   that cannot fail (#890), coverage that under-reports (#767), and tests that
   mutate your real `~/.jmo/config.yml` and `.jmo/history.db` (#933, #802).
   Fixing instruments before taking 80 measurements is what makes the
   measurements mean anything.
2. **#808 precedes #861.** #808 deletes six dead discovery helpers and rehomes
   **129 tests** written against dead code. Doing #861 first means migrating
   those 129 tests through a path-normalisation change for no reason.
3. **#861 precedes Phases 5, 6 and 7.** `location.path` normalisation changes
   `common_finding.fingerprint()`, which every downstream artifact, diff baseline
   and dashboard render keys on. Anything fixed downstream first gets
   re-validated.
4. **Phase 7 (dashboard) follows Phase 4.** The dashboard renders
   `location.path`; building it before normalisation ships a dashboard that
   displays four spellings of one file.
5. **Phase 8 (docs) is last.** Documentation describes behaviour. Write it once
   behaviour is final.

## Phase 4 — The data path, upstream-first

**6 issues, in this order:** #861 → #837 → #848 → #845 → #846 → #849

**This is the phase the whole ordering exists to protect.** The order mirrors
`normalize_and_report.py:gather_results`.

- **#861 — `location.path` is unnormalised.** One `deep` scan of one directory
  produced **four spellings of the same file**: 149 of 242 paths contain a
  backslash, 64 carry a leading separator, 66 are absolute. Against a ground
  truth of 77 findings in one file, dedup is measurably wrong — and **the host's
  absolute path ships in SARIF and the dashboard**. This was deferred as a
  migration only because it changes `fingerprint()` and invalidates baselines;
  with no users there are no baselines to protect.
- **#837 — every adapter discards the tool's own error channel**, so a file a
  scanner *could not analyse* is reported as clean. **0 of 8** adapters read it.
  For a security tool this is the most consequential defect in the backlog: a
  false negative that looks like a pass.
- **#848** Phase-1 dedup silently discards any finding with a falsy `id`.
- **#845** CWEs present in tool output never reach `risk.cwe`, starving every
  compliance mapping downstream.
- **#846** `RULE_EQUIVALENCE` declares genuinely different controls equivalent.
- **#849** EPSS makes one HTTP request per finding with an unknown CVE and builds
  an unbounded bulk URL.

**Measure first:** capture a real `deep` scan's findings **before** any change —
path spellings, fingerprints, dedup counts, `risk.cwe` fill rate — as the
comparison corpus. Note that ~67% of `history.db` is test/dogfood noise, so any
assertion built on it measures noise unless filtered.

**Acceptance:** one file yields one path spelling; no host absolute path appears
in any exported artifact; a file a tool failed to read is reported as an error,
not as clean; dedup counts move in the measured direction and the movement is
explained.

## Closing keywords: what actually fires

Three sessions wrote `Closes #N` in a PR body targeting `dev` and closed
nothing. Two documents then disagreed about why, and **both were wrong**. What
follows is measured, 2026-08-26.

| PR | base | `closingIssuesReferences` | keywords in its squash commit |
|---|---|---:|---:|
| #978 (Phase 0) | `dev` | **0** | 17 |
| #995 (Phase 1) | `dev` | **0** | **0** |
| #997 (Phase 2) | `dev` | **0** | **0** |
| #986 (the last sync) | `main` | **86** | 93 |

**GitHub creates closing references only for a PR whose base is the default
branch.** A `Closes #N` in a PR body aimed at `dev` is not "a link that fires
later" — GitHub never records it at all. That is why all three phase PRs report
zero, and why a body-only keyword is unrecoverable once the branch is deleted.

So the two standing explanations were each half right and, combined, misleading:

- *"Keywords go in the PR body; a PR into `dev` links but does not close"* —
  **false in its load-bearing half.** There is no link. #986 worked because its
  base was `main`, not because bodies work.
- *"A squash merge drops the PR body"* (#1000) — **true, but not the mechanism.**
  The body was already inert. And a squash does *not* drop commit messages: it
  concatenates them, which is exactly what makes the commit path work.

**The path that survives, measured end to end:** `b92b8cf` (Phase 0's squash into
`dev`) carries 17 keywords because its branch's individual commits carried them;
the `dev → main` squash `3fb64fb` then carries **93** in a 246 KB, 4,665-line
message, GitHub accepted it, and all 17 Phase 0 issues are CLOSED. A keyword in a
commit message survives two consecutive squashes.

**Rule: put `Closes #N` in an individual commit message.** The PR body may repeat
it for readers; it is not what fires. The sync PR's body is a *belt* — useful,
because its base is `main` so it does work there — but the commit is the braces,
and it is written by the session that knows.
