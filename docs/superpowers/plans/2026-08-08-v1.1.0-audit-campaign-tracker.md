## How to mark a finding off

Every finding ends in one of four states. **All four count as resolved.**

- `[x] FIXED` — changed the behaviour; say what changed
- `[x] DELETED` — removed the dead thing rather than repairing it
- `[x] DISMISSED` — verified against the code and the claim is wrong; **say why**
- `[x] BLOCKED-UNVERIFIABLE` — cannot be checked here; **state the missing
  prerequisite and what would unblock it**

Tick the box, append the verdict inline, and update the Progress table **in the
same commit**. A finding without a stated verdict is not resolved.

**DISMISSED requires evidence, not judgement.** Today's session produced two
claims that looked like findings and were not: a "29 vs 27 adapter mismatch"
(the directory holds 27 adapters plus `__init__.py`, `base_adapter.py` and
`common.py`) and "osv-scanner is fully wired" (it is in exactly one registry
table). Both were caught by measuring. Dismiss the same way.

### The measurement that determined the design

Filed as **#861** at chunk-8 closeout, after this section was written — hence
the measurement below without a number until chunk 9 added the citation.

`location.path` is not written uniformly. **One `deep` scan of one directory
produced four spellings of the same file** — 149 of 242 paths contain a
backslash, 64 carry a leading separator, 66 are absolute:

| spelling | count |
|---|---:|
| `iac/aws-s3-public.tf` | 36 |
| `\iac\aws-s3-public.tf` | 34 |
| `C:\...\fixturecopy\iac\aws-s3-public.tf` | 6 |
| `iac\aws-s3-public.tf` | 1 |

Against a ground truth of **77 findings in that one file**:

| matcher | matched |
|---|---:|
| naive `fnmatch(path, pattern)` | **37 of 77 (48%)** |
| separator-normalized | 71 of 77 |
| normalized + component-boundary suffix | **77 of 77** |

So the obvious implementation suppresses under half the findings in a file the
user named explicitly — *worse* than the total failure it replaces, because it
looks like it works. Path normalization is adapter-layer state chunk 8 only
consumes; it is recorded here as a constraint, not fixed here.

**`fnmatch` is also platform-dependent** — it applies `os.path.normcase`, which
lowercases on Windows only. Measured on the same corpus: `IAC/*` matched **101**
findings on Windows and **0** on POSIX; `*.TF`, **77** and **0**. A config
committed to a repository would suppress different findings on a developer's
machine than in CI, so matching uses `fnmatchcase` with explicit normalization.

### The stored XSS, proven end to end

The escaper replaced the single literal `</script>`. **The HTML tokenizer matches
an end tag case-insensitively** and terminates on whitespace, `/` or `>`, so
three spellings broke out. Parsed with `html.parser`, counting elements that land
outside the `<script>` element:

| payload | before | after |
|---|---|---|
| `</script>` | contained | contained |
| **`</SCRIPT>`** | **`<img src=x onerror=…>` parsed as live markup** | contained |
| **`</ScRiPt>`** | **breakout** | contained |
| **`</script >`** | **breakout** | contained |
| `</script/>`, `</script\t>`, `</script\n>` | contained | contained |

**Reachability was measured through the real thing, not composed from two
facts.** `context.snippet` / `context.code_snippet` carry the literal line from


fix the identical scan yields **0** breakout elements, raw `</SCRIPT>` count
**0**, and the payload text still present twice — preserved as data.

The fix escapes `<`, `>` and `&` as `\uXXXX`. That form is **valid JSON as well

### The two most serious

- [x] **FIXED** — **`jmo history query` could destroy the database, and
      reported the destruction as a failure.** `cmd_history_query` ran
      `cursor.execute(args.query)` on a read-write connection with no
      restriction on statement type. Measured on a throwaway copy of the real
      schema:

      | SQL | rc | message | persisted? |
      |---|---|---|---|
      | `SELECT 1` | 0 | table | — |
      | `DELETE FROM scans` | 1 | `SQL Error: 'NoneType' object is not iterable` | **no** — rolled back |
      | `UPDATE scans SET branch='pwned'` | 1 | *same message* | **no** — rolled back |
      | `DROP TABLE scans` | 1 | *same message* | **YES — table gone** |
      | `CREATE TABLE evil(x)` | 1 | *same message* | **YES — table created** |

      DDL executes in autocommit and is permanent; DML opens an implicit
      transaction that `conn.close()` discards. **So one message meant
      "destroyed your data" and "silently did nothing" depending on the
      statement**, and in both cases claimed to have failed. The default
      database is ~1 GB and is the only copy. The message was not even a
      database error — it is a `TypeError` from `cursor.description` being
      `None` for non-SELECT, caught by the broad `except Exception`.
      Fixed by opening the database **read-only** (`?mode=ro`) so SQLite is the
      guard: a `startswith("SELECT")` allowlist would have to parse SQL
      correctly to be safe, which is the "guard matching its own literals"
      shape. After: all four write statements refused with
      `SQL Error: attempt to write a readonly database`, tables intact.
- [x] **FIXED** — **no read command could read a read-only database.**
      `get_connection` issued `PRAGMA journal_mode=WAL` unconditionally. That
      is a persistent on-disk property, so it is a write:

      ```
      Error getting stats: attempt to write a readonly database
        File "scripts/core/history_db.py", line 279, in get_connection
          conn.execute("PRAGMA journal_mode=WAL;")
      ```

      — a raw traceback, rc=1, for `stats`, `list` and every other read. This
      matters because `docs/DOCKER_README.md` recommends mounting `.jmo/` as a
      volume; a read-only mount, an archived database, or a snapshot kept as a
      fixture all hit it. WAL is an optimisation, not a requirement, so it is
      now best-effort. After: rc=0, correct output, and the unwritable file is
      left **byte-identical** (sha unchanged, header still `write_ver=1`).
