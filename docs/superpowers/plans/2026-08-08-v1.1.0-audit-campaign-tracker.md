## How to mark a finding off

Every finding ends in one of four states. **All four count as resolved.**

- `[x] FIXED` — changed the behaviour; say what changed
- `[x] DELETED` — removed the dead thing rather than repairing it
- `[x] DISMISSED` — verified against the code and the claim is wrong; **say why**
- `[x] BLOCKED-UNVERIFIABLE` — cannot be checked here; **state the missing
  prerequisite and what would unblock it**

Tick the box, append the verdict inline, and update the Progress table **in the
same commit**. A finding without a stated verdict is not resolved.

**DISMISSED requires evidence, not judgement.** Today's session produced two
claims that looked like findings and were not: a "29 vs 27 adapter mismatch"
(the directory holds 27 adapters plus `__init__.py`, `base_adapter.py` and
`common.py`) and "osv-scanner is fully wired" (it is in exactly one registry
table). Both were caught by measuring. Dismiss the same way.

would have driven the acceptance corpus to zero findings and made the
measurement meaningless. Scanning a copy at a path the config does not name
keeps it usable. **Watch the denominator:** these are two different corpora and
neither is a percentage of the other.

### The measurement that determined the design

Filed as **#861** at chunk-8 closeout, after this section was written — hence
the measurement below without a number until chunk 9 added the citation.

`location.path` is not written uniformly. **One `deep` scan of one directory
produced four spellings of the same file** — 149 of 242 paths contain a
backslash, 64 carry a leading separator, 66 are absolute:

| spelling | count |
|---|---:|
| `iac/aws-s3-public.tf` | 36 |
| `\iac\aws-s3-public.tf` | 34 |
| `C:\...\fixturecopy\iac\aws-s3-public.tf` | 6 |
| `iac\aws-s3-public.tf` | 1 |

Against a ground truth of **77 findings in that one file**:

| matcher | matched |
|---|---:|
| naive `fnmatch(path, pattern)` | **37 of 77 (48%)** |
| separator-normalized | 71 of 77 |
| normalized + component-boundary suffix | **77 of 77** |

So the obvious implementation suppresses under half the findings in a file the
user named explicitly — *worse* than the total failure it replaces, because it
looks like it works. Path normalization is adapter-layer state chunk 8 only
consumes; it is recorded here as a constraint, not fixed here.

**`fnmatch` is also platform-dependent** — it applies `os.path.normcase`, which
lowercases on Windows only. Measured on the same corpus: `IAC/*` matched **101**
findings on Windows and **0** on POSIX; `*.TF`, **77** and **0**. A config
committed to a repository would suppress different findings on a developer's
machine than in CI, so matching uses `fnmatchcase` with explicit normalization.

### The stored XSS, proven end to end

The escaper replaced the single literal `</script>`. **The HTML tokenizer matches
an end tag case-insensitively** and terminates on whitespace, `/` or `>`, so
three spellings broke out. Parsed with `html.parser`, counting elements that land
outside the `<script>` element:

| payload | before | after |
|---|---|---|
| `</script>` | contained | contained |
| **`</SCRIPT>`** | **`<img src=x onerror=…>` parsed as live markup** | contained |
| **`</ScRiPt>`** | **breakout** | contained |
| **`</script >`** | **breakout** | contained |
| `</script/>`, `</script\t>`, `</script\n>` | contained | contained |

**Reachability was measured through the real thing, not composed from two
facts.** `context.snippet` / `context.code_snippet` carry the literal line from
the scanned file — 60 of 242 findings in the fixture corpus have one. Appending

```text
</SCRIPT><img src=x onerror=alert(document.domain)>AWS_ACCESS_KEY_ID=AKIAIOSFODNN7EXAMPLE
```

to a scanned `.env` and running `jmo scan --tools horusec` put it into
`dashboard.html` as `"code_snippet": "</SCRIPT><img …"`, and the parser found
**2 live `<img onerror>` elements outside `<script>`**. The template's CSP is
`script-src 'unsafe-inline' 'self'`, so it does not stop the handler. After the
fix the identical scan yields **0** breakout elements, raw `</SCRIPT>` count
**0**, and the payload text still present twice — preserved as data.

The fix escapes `<`, `>` and `&` as `\uXXXX`. That form is **valid JSON as well
as valid JavaScript**; the previous `<\script` and `<\!--` were legal JS but
illegal JSON, so the embedded payload could not be round-tripped.

**The same broken escaper existed at two more sites** in `diff_html_reporter.py`
(`:148`, `:219`). Fixing one and leaving two is chunk 5's mistake — the NDJSON
sibling that stayed silent while its twin was fixed. All three now call one
`escape_json_for_script`.

## Chunk 22 — backlog reconciliation + release readiness

**Must be last. The v1.1.0 tag waits on this chunk.**

**Surface:** the GitHub issue tracker, `docs/KNOWN_LIMITATIONS.md`, and the
campaign's own completion claim.

**Why it exists.** Added at the close of chunk 9, when the drift became
measurable: **112 issues open, roughly 40 claimed by no chunk.** Every one had
been filed correctly — the routing worked. None had been *scheduled*. Filing an
issue feels like resolving it and is not, so "campaign complete = release" could
have been stated truthfully while a large backlog shipped unexamined. See the
second half of the release bar in
[the strategy doc](2026-08-08-v1.1.0-audit-campaign.md#release-bar-locked).

**Known going in**

- [ ] **Seven auto-filed nightly-failure issues, six with zero comments** —
      **#724 #812 #817 #818 #821 #839 #844**, one per night from 2026-08-07.
      **#839** is explicitly recorded as UNDIAGNOSED and predates the chunk-6
      branch, so it is not caused by campaign work. This is the largest single
      cluster and the most likely to be hiding a real regression behind a
      tripwire nobody reads.
- [ ] **#718 reads OPEN although it is complete (103/103).** Either it closes at
      `dev → main` or it needs closing by hand — check which before assuming.
- [ ] **Split-outs no chunk claims:** **#808 #837 #845 #861 #862**. Each is
      marked "its own PR" in the handoff, which is a route, not a slot.
- [ ] **Pre-campaign backlog:** #716 #721 #722 #723 #727 #731 #732 #733 #740
      #742 #747 #748 #750 #752 #755 #756 #757 #758 #761 #765 #767 #768 #769
      #770 #772 #773 #782 #784 #792 #795 #796 #800 #801 #802 #824 #825 #833
      #834. **Re-derive this list rather than trusting it** — chunks 10-21 will
      have closed some and added others.
- [ ] **ROADMAP issues (#34 #37 #38 #48 #49 #52-#55) are features, not
      findings.** They are not campaign scope and should not be dragged into it;
      `DEFER-POST-1.1.0` is the honest disposition for the whole set, decided
      once rather than nine times.

**Phase 1 — nightly-failure archeology.** Take the seven together, not one at a
time; they are likely one or two root causes. **Grep the raw job logs for
`+++ Timeout`, never for `FAILED`** — a pytest-timeout dump *replaces* the
summary. `gh run view --log` returns no pytest output; use
`gh api repos/<r>/actions/jobs/<id>/logs`. Watch for `--maxfail` truncation: a
visible failure count of exactly 20 means there are more underneath.

> **If phase 1 turns out to be deep, split it into its own chunk** rather than
> shrinking it to fit. That is the protocol, and this chunk is the one most
> exposed to the pressure toward false completion — it is the last one, and the
> tag is behind it.

**Phase 2 — disposition every remaining open issue.** One of
`BLOCKS-v1.1.0` / `SHIP-WITH-IT` / `DEFER-POST-1.1.0` / `CLOSE` /
`BLOCKED-UNVERIFIABLE`, recorded **on the issue**, with a reason for anything
deferred. Anything `SHIP-WITH-IT` that a user can actually hit goes into
`docs/KNOWN_LIMITATIONS.md` — that is the difference between an accepted
limitation and an undocumented bug.

**Phase 3 — release readiness.** Only after phases 1 and 2:

- `dev → main` fast-forward still clean, and the closing keywords fire.
- Confirm the issues marked "fixed on `dev`, closes at `dev → main`" actually
  closed. They read OPEN until then; that is expected, and it is also exactly
  where a missed one hides.
- `CHANGELOG.md` is written **at release time** in this repo, so it is written
  here — from the per-chunk "user-visible changes" sections accumulated in the
  handoff, not by re-reading diffs. Chunk 9's includes a `### Security` entry.
- Run the `release-readiness` agent and `jmo validate --tier full`.

**Acceptance:** **zero issues without a disposition** — not zero open issues.
An issue deliberately deferred with a stated reason is discharged. An issue
nobody looked at is not, however small it looks. State the final counts:
open, and the split across the five dispositions.
