## How to mark a finding off

Every finding ends in one of four states. **All four count as resolved.**

- `[x] FIXED` — changed the behaviour; say what changed
- `[x] DELETED` — removed the dead thing rather than repairing it
- `[x] DISMISSED` — verified against the code and the claim is wrong; **say why**
- `[x] BLOCKED-UNVERIFIABLE` — cannot be checked here; **state the missing
  prerequisite and what would unblock it**

Tick the box, append the verdict inline, and update the Progress table **in the
same commit**. A finding without a stated verdict is not resolved.

**DISMISSED requires evidence, not judgement.** Today's session produced two
claims that looked like findings and were not: a "29 vs 27 adapter mismatch"
(the directory holds 27 adapters plus `__init__.py`, `base_adapter.py` and
`common.py`) and "osv-scanner is fully wired" (it is in exactly one registry
table). Both were caught by measuring. Dismiss the same way.

### The measurement that determined the design

Filed as **#861** at chunk-8 closeout, after this section was written — hence
the measurement below without a number until chunk 9 added the citation.

`location.path` is not written uniformly. **One `deep` scan of one directory
produced four spellings of the same file** — 149 of 242 paths contain a
backslash, 64 carry a leading separator, 66 are absolute:

| spelling | count |
|---|---:|
| `iac/aws-s3-public.tf` | 36 |
| `\iac\aws-s3-public.tf` | 34 |
| `C:\...\fixturecopy\iac\aws-s3-public.tf` | 6 |
| `iac\aws-s3-public.tf` | 1 |

Against a ground truth of **77 findings in that one file**:

| matcher | matched |
|---|---:|
| naive `fnmatch(path, pattern)` | **37 of 77 (48%)** |
| separator-normalized | 71 of 77 |
| normalized + component-boundary suffix | **77 of 77** |

So the obvious implementation suppresses under half the findings in a file the
user named explicitly — *worse* than the total failure it replaces, because it
looks like it works. Path normalization is adapter-layer state chunk 8 only

findings on Windows and **0** on POSIX; `*.TF`, **77** and **0**. A config
committed to a repository would suppress different findings on a developer's
machine than in CI, so matching uses `fnmatchcase` with explicit normalization.

### Design constraints worth not re-deriving

- **A results directory is not evidence of what was scanned.** It records
  outputs. Anything about the *target* — branch, commit, repo identity — must be
  passed forward from the scan, which is why `repo_paths` now exists in
  `.scan_metadata.json`. Deriving it later is guessing that looks like data.
- **NULL beats a plausible value.** `store_scan()` deliberately records nothing
  rather than something defensible-looking. The 1633 NULL rows are the honest
  half of the old behaviour; the 13 non-NULL ones are the dishonest half.
- **A schema claim in a test fixture is not the schema.** #895's premise came
  from `DEFAULT '1.0.0'` in `tests/cli/test_history_commands.py`. Production has
  `NOT NULL` and no DEFAULT — the opposite constraint. A fixture that is more
  permissive than production cannot fail where production would.
- **Default arguments freeze module constants at import.**
  `def get_connection(db_path: Path = DEFAULT_DB_PATH)` cannot be redirected by
  monkeypatching `DEFAULT_DB_PATH`. This is why #802 is not fixable by a
  conftest fixture, and why `test_history_db.py` patches `sqlite3.connect`
  instead.
- **`jmo history verify` was already correct.** Its exit code sits outside the
  format branch. Keeping the correct sibling in the same test matrix is what
  makes the other two demonstrably wrong rather than stylistically different.

> **Every policy decision is exercised against both a findings file known to

### Acceptance criterion

> **Every `schedule` subcommand is exercised against both a schedule that
> exists and one that does not, and every mutation is verified by reading
> `~/.jmo/schedules.json` back — so that a success message proves the write
> happened, rather than proving the command returned 0. Four outputs are
> checked: the exit code, the human output, the persisted JSON, and the
> exported workflow file.**

Naming the outputs is the point. Chunk 16's criterion caught a second consumer
of the same engine only because it named the `POLICY_REPORT.md` artifact
explicitly. Chunk 15's was correct about selection and silent about rendering,
and it passed while the report printed `STABLE +0` over a -90.6% window.

The clauses, and why each one is here:

1. **Round-trip, not return code.** A scheduler's failure mode is silence. A
   schedule that was never persisted, a cron entry never installed, and a
   broadcast never sent all look exactly like "nothing was due yet" — there is
   no error to notice. No success message is accepted here that has not been
   confirmed against the state it claims to have changed.
2. **Both arms, every subcommand.** `get`/`update`/`export`/`install`/`delete`/
   `validate` all open with the same `manager.get(...) or return 1`;
   `uninstall` does not. That asymmetry is invisible unless the missing-name
   arm is actually run.
3. **The exported file is an artifact, and artifacts get parsed.** `export`
   writes YAML that no parser in this repo has ever loaded — chunk 10's
   phantom-artifact shape, where five artifacts reconciled exactly with each
   other while their SARIF carried 340 schema errors. The YAML must parse, the
   cron expression must survive the round trip into it, and the schedule's
   declared `timezone` must either appear in the output or be reported as
   unsupported.
4. **The persisted JSON is read back through the reader, not just eyeballed.**
   `schedule_manager` serialises with `asdict()` and rehydrates with
   `Dataclass(**data)`. A field the writer emits that the reader cannot accept
   is a corruption that surfaces on the *next* invocation and never on the one
   that wrote it.
5. **The email path is decided, not skipped.** `resend` is an optional extra
   (`pyproject.toml` `email = ["resend>=2.0"]`) and is not installed;
   `RESEND_API_KEY` is unset. Both gates return early. That is either correct
   optional-dependency degradation or a fail-open, and it is settled by
   evidence — by patching the transport, never by supplying a credential.
   `email_service.py:61` hardcodes a **production** audience id as the default
   for `RESEND_AUDIENCE_ID`; the safety here comes from the key being absent,
   not from the target being a test audience.
